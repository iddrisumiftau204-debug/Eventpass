# EventPass — Requirements & Scope

Reverse-documented from the shipped implementation in `backend/` and
`frontend/` — this describes what the system actually does and
enforces, not an aspirational spec written before the code existed.

## Purpose

A small event ticketing and check-in tool for a single organizer role:
create events, register attendees against them, and check attendees in
at the door using a generated ticket code (typed, or scanned as a QR
code).

## Actors

- **Organizer** — the only authenticated role. Registers an account,
  creates events, registers attendees, and checks people in. Can only
  see and modify their own events and attendees.
- **Attendee** — never logs in. Exists only as a row created by an
  organizer, identified by a ticket code. Presents that code (or its
  QR encoding) at the door.

There is no admin role, no multi-organizer collaboration on one event,
and no self-service attendee registration — an organizer enters every
attendee by hand (or presumably from a spreadsheet, but there's no
import feature).

## Functional requirements

Numbered to match how they map onto the API/tests, not an external
spec — kept here for traceability.

- **FR1** — An organizer can register an account with name, email,
  password. Email must be unique across all organizers.
- **FR2** — An organizer can log in with email/password and receive a
  bearer token valid for 12 hours.
- **FR3** — An organizer can create an event with a name and date
  (required), plus optional venue and capacity.
- **FR4** — An organizer can list, view, update, and delete only their
  own events.
- **FR5** — Deleting an event deletes its attendees too (no orphaned
  attendee rows).
- **FR6** — An organizer can register an attendee (name + email) to
  one of their own events.
- **FR7** — The same email cannot be registered twice for the *same*
  event, but can be registered for different events.
- **FR8** — Every registered attendee is issued a ticket code,
  generated by the system — the organizer does not supply it. The code
  is guaranteed unique across all attendees, not just within one event.
- **FR9** — An organizer can look up a ticket by code without checking
  it in (e.g. to verify it before someone reaches the door).
- **FR10** — An organizer/staff member can check in a ticket by code.
  A successful check-in records a timestamp.
- **FR11** — A ticket can only be checked in once. A second attempt on
  an already-checked-in code is rejected (not silently accepted, not
  double-recorded) and reports when the first check-in happened.
- **FR12** — Checking in a code that doesn't exist is rejected and
  distinguishable from "already checked in" (different status code).
- **FR13** — An event's detail view shows live counts: how many are
  registered, how many are checked in, and the check-in percentage.
- **FR14** — A ticket's code is also rendered as a scannable QR code
  (encoding the raw code string) so it can be checked in without
  manual typing, and can be printed per-attendee.

## Non-functional requirements

- **NFR1 — Check-in correctness under concurrency.** The critical
  failure mode for a system like this is double-admitting one ticket
  because two devices scanned it in the same instant. FR11 must hold
  even when multiple check-in requests for the same code arrive
  concurrently — exactly one succeeds, the rest are rejected as
  duplicates. This is the one requirement with a dedicated automated
  test firing simultaneous requests (see
  `backend/tests/checkin.test.js`), because it's the one requirement
  that's easy to get wrong with a naive read-then-write implementation
  and hard to catch by manual testing.
- **NFR2 — Data isolation.** One organizer must never be able to read
  or modify another organizer's events, attendees, or tickets, even
  with a valid token for their own account. Enforced by scoping every
  query to `organizerId = req.user.id` (directly for events, via the
  owning event for attendees/tickets).
- **NFR3 — Zero-install local setup.** SQLite via `better-sqlite3`, no
  external database service to stand up, so `npm install && npm run
  dev` in both `backend/` and `frontend/` is the entire setup. Chosen
  because this project was built under a time-boxed exam constraint
  where setup friction is wasted time.
- **NFR4 — Fast, keyboard/scanner-friendly check-in.** The `/checkin`
  screen auto-focuses its input and refocuses after every submission,
  so a staff member scanning a QR code (which types-and-submits like a
  keyboard) or typing codes by hand can process a queue without
  touching the mouse between attendees.
- **NFR5 — Ticket codes must be legible when read aloud or transcribed
  by hand.** 7 characters, uppercase letters + digits, with `0/O` and
  `1/I` excluded from the alphabet.

## Explicitly out of scope

These were considered and deliberately left out, either because the
time-boxed build didn't call for them or because they'd need product
decisions this project doesn't make:

- **Capacity enforcement.** `events.capacity` is stored but nothing
  checks registered-attendee count against it — you can over-register
  an event with no warning.
- **Attendee-facing anything.** No self-registration, no emailed
  ticket, no attendee login or ticket-status page. An organizer must
  deliver the ticket code/QR to the attendee out-of-band (the "print
  ticket" button exists for this — the organizer prints/hands it over
  in person or exports it themselves).
- **Undo check-in.** Once checked in, there's no API to reverse it
  (e.g. for a mis-scan) short of editing the database directly.
- **Multi-organizer / staff accounts per event.** One organizer =
  one login = full access to their own events. No way to grant a
  door-staff account restricted to check-in only.
- **Password reset, email verification, rate limiting on auth
  endpoints.** Registration/login are functional but bare — no forgot
  password flow, no lockout after repeated failed logins.
- **Payments / paid ticketing.** "Ticket" here means an admission
  record, not a purchased good — there's no price, no payment
  integration.

## Acceptance criteria (as tested)

The backend test suite (`backend/tests/`) is the executable version of
the acceptance criteria that were considered important enough to
automate:

1. Generated ticket codes match the expected shape (7 chars, excluded-
   ambiguous-character alphabet) and `generateUniqueTicketCode` never
   returns a code already present in the database, across repeated
   generation against a growing table.
2. A valid, unused ticket code checks in successfully and returns a
   timestamp (FR10).
3. Checking in the same code twice returns 409 on the second call,
   with the *original* check-in time, not a new one (FR11).
4. Checking in an unknown code returns 404 (FR12).
5. Five simultaneous check-in requests against one fresh code result
   in exactly 1 success and 4 conflicts (NFR1).
6. Registering the same email twice to the same event is rejected with
   409 `DUPLICATE_EMAIL` (FR7).

Everything else (auth, event CRUD, stats, the QR/print UI) is covered
by manual/driven UI verification rather than an automated suite — see
`backend/README.md` and `frontend/README.md` for what to check by hand.
